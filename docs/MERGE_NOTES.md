# Объединение A2S-сборки и Rust+ (fixed11): что сделано и как проверить

**Основа — A2S-сборка.** Из fixed11 перенесено только то, чего в ней не было: вкладка «Rust+ Устройства», Team Chat-команды Smart Switch (`DeviceCommands.cs`, `RustPlusDevices.cs`, тесты). Авторизация Rust+, сопряжение серверов, FCM-слушатель, Manager, Smart Alarm/Switch в A2S-сборке уже были и сохранены.

> Текущая версия собирается .NET 10 SDK, включая WPF/XAML; автоматические тесты Core выполняются на Linux с `EnableWindowsTargeting=true`. Запуск и проверка реального Rust+ сервера требуют Windows и игры.

## 1. База данных (SQLite)
- История A2S-миграций v1–v7 **не менялась** (v7 по-прежнему переименовывает `bm_id→source_key`, `bm_player_id→player_key`).
- Миграция fixed11 «v7» (таблицы Team Chat-команд устройств) перенесена в **v8**, сделана идемпотентной (`IF NOT EXISTS`).
- **v9**: `watch_entries.identity_level`, `player_names`, `known_servers`.
- **v10**: `rp_servers.rustplus_id`, достоверная синхронизация устройств (`added_at`, `last_sync_at`, `last_is_on`) и постоянные карточки `rp_device_pairing_requests`.
- `RepairSchema` перенесён из fixed11 и исправлен: учитывает `RENAME COLUMN` (раньше он заново добавлял устаревший `bm_id` из v2 и не знал про `source_key`), собирает `CREATE TABLE` с правильным порядком столбцов и ограничений, вызывается после миграций (в т.ч. после восстановления из повреждённой БД).
- База, созданная fixed11 на своей v7 (столбцы `bm_id`/`bm_player_id`), переименовывается **на месте с сохранением данных**: `servers.source_key = host:port`, `watch_entries.player_key = ник`, «недавние серверы» BattleMetrics очищаются. Ошибка `no such column: source_key` на такой базе устранена.
- Перед миграцией по-прежнему создаётся копия `<база>.bak-v<версия>`. Пользовательские данные не удаляются.
- Отдельного `EnsureSchema` в A2S-сборке не было; дублирования нет (единственный механизм — миграции + RepairSchema).

## 2. BattleMetrics
В A2S-сборке кода BattleMetrics нет (API, сервисы, токен, настройки, UI, зависимости отсутствуют). Остались только имена `bm_id`/`bm_player_id` внутри исторических миграций v2/v5/v7 — их менять нельзя, иначе сломается обновление существующих баз. Уведомления о входе и порогах групп удалены (см. п. 7); константы `WatchJoin`/`WatchGroup` убраны.

## 3. Единый источник состояния Rust+ (`RustPlusHub`)
Выбранный сервер, список серверов, события изменения списка устройств, последнее состояние и доступность устройств хранятся в одном `RustPlusHub`. Обе вкладки читают только его: выбор сервера в «Rust+» сразу становится выбором в «Rust+ Устройства» и наоборот; добавление/удаление/переименование устройства и FCM-события обновляют обе вкладки. Подключение к новому серверу выбирает его один раз, но периодические обновления выбор пользователя не сбрасывают.

## 4. Обнаружение устройств (причины и исправления)
В Rust+ список устройств у сервера запросить нельзя: обнаружение выполняется по push после нажатия Pair в игре. Текущий поток: FCM → постоянная карточка обнаружения → «Проверить и добавить» → реальный `getEntityInfo` → сохранение в SQLite. Одного Entity ID или самого FCM-события недостаточно для записи устройства. Отдельных accept/reject-команд протокол не имеет; «Скрыть» действует только локально.
1. Событие больше не приписывается подключённому/выбранному серверу. `FcmServerResolver` сначала использует точный Rust+ Server ID, фильтрует по Player ID, затем использует адрес/порт; без идентификаторов допускается только единственный однозначный сервер того же игрока.
2. Поддержаны реальные формы `OnEntityPairing` (`Data.EntityId/EntityType/EntityName`, `ServerId`, `PersistentId`) и специализированных событий, где Entity ID находится непосредственно в `Data`. JSON `body` по-прежнему раскрывается для совместимости.
3. Повторы FCM дедуплицируются по `PersistentId` и ожидающей паре сервер/Entity ID. Скрытая или обработанная карточка не открывается повтором того же сообщения; ошибка проверки не сохраняет устройство и остаётся видимой на карточке.
4. Слушатель FCM отделён от вкладок; обе вкладки получают изменения карточек, устройств и состояний через общий `RustPlusHub`.

Сопряжение сервера по push тоже обрабатывается (если пришли адрес, порт, playerId и токен). Токены в журнал не пишутся.

## 5. Smart Alarm, колокольчик
Колокольчик 🔔 — только у Smart Alarm, в обеих вкладках, сохраняется сразу (`rp_devices.alarm_notify`). Текст уведомления: «СРАБОТАЛА СИГНАЛИЗАЦИЯ! Устройство: …. Сервер: ….» (в Overlay — с переводами строк). Срабатывание по websocket и по FCM дедуплицируется (окно 10 с). Колокольчик выключен — событие пишется в историю устройства, уведомления нет.
Если push о срабатывании не содержит `entityId`, устройство ищется по названию. Неизвестная сигнализация больше не добавляется автоматически: сначала требуется карточка сопряжения и успешная проверка. Значение Smart Alarm отображается только как активность сигнала, не как питание/охрана; квадрат состояния остаётся серым.

## 6. Доступность (`DeviceAvailabilityService`)
Опрос Smart Switch и Smart Alarm раз в 30 с (настройка `DeviceProbeSeconds`, не менее 10), 3 неудачных чтения подряд (`DeviceProbeFailures`) → «недоступно» (одно уведомление), первое удачное чтение → отдельное уведомление «снова доступно». Потеря связи с сервером не засчитывается: при неудаче делается проверка самого сервера (`PingAsync`); если он не отвечает — счётчики сбрасываются, устройства остаются «неизвестно». Без соединения опроса нет. Причина недоступности не утверждается (текст не говорит «уничтожено»).

## 7. Уведомления
Для каждого из четырёх типов (срабатывание сигнализации, недоступность, восстановление, выход игрока) — выбор: **Отключено / Team Chat / Overlay / Team Chat и Overlay** (вкладка «Уведомления», блок «Игровые уведомления»; хранится в настройках, переживает перезапуск; по умолчанию Overlay). Team Chat отправляется только при активном соединении Rust+ **с тем же сервером**; иначе в «Журнале доставки» будет явная причина («нет активного соединения…», «соединение с другим сервером…»). Для игроков сервер сопоставляется по IP (в A2S и Rust+ разные порты). Показывается реальный результат каждой отправки.
Telegram/Discord и Windows-уведомление выхода игрока работают по-старому (в разделе «Остальные события»).

## 8–12. Игроки, достоверность, индикаторы, выход
- **Уровни** (`IdentityLevel`): *Подтверждено Steam* (Steam Web API сейчас сам сообщает сервер игрока, нужен ключ API и SteamID64), *Подтверждено пользователем* (кнопка «Связать SteamID64» у записи наблюдения), *не подтверждено* (только ник из A2S). Уровни не смешиваются; Steam-подтверждение вычисляется на лету и не хранится. Данные Steam сопоставляются строго: IP и порт запросов должны совпасть, иначе результат «неопределённо» (не гадаем); отсутствие данных ≠ отсутствие на сервере.
- **Индикатор ■**: зелёный — на сервере, красный — подтверждённо отсутствует (после серии успешных проверок, а не при единичном «не найден»), серый — неизвестно **или** игрок найден только по нику. Обновляется каждым циклом мониторинга; подсказка объясняет основание.
- **Уведомляется только выход.** Вход, возвращение, смена сервера и пороги групп не уведомляются (запись в историю остаётся). Защита от повторов: ключ события в БД (переживает перезапуск) + интервал `NotifyMinIntervalSeconds`. Для не подтверждённой личности в тексте есть пометка «по нику, не подтверждено».
- **Собственная база**: `ServerCrawler` опрашивает известные серверы (наблюдаемые + открытые в поиске), не чаще `CrawlerPollSeconds` (≥60 с) на сервер, не более `CrawlerMaxServersPerCycle` за цикл, последовательно через общий rate limiter и кэш снимков; история посещений/сессий пишется в `presence_history` (очистка старше `PresenceRetentionDays`). История ников по SteamID64 — `player_names` (пополняется ником из Steam и вашей привязкой). Кнопка «Где ещё наблюдался» ищет ник (и известные ники привязанного SteamID64) по всей базе — результат помечен как совпадение по нику.
- **Ограничения A2S**: список игроков не содержит SteamID64; время входа/выхода — расчётное по моментам опроса, не точное; «выход» — это «не обнаружен в полном списке после нескольких проверок».

## Чек-лист проверки на реальном сервере
1. Собрать и запустить тесты: `dotnet test`. Открыть приложение на **копии** своей рабочей базы; убедиться, что рядом появился `.bak-v7`, а ошибок `no such column` нет (журнал/`startup-error.txt`).
2. Вкладка «Rust+»: вход через Steam, «Ждать сопряжения», в игре Pair with server. Строка «Приём push-уведомлений» должна стать «запущен». Если пишет ошибку — приложить текст (имена методов библиотеки RustPlusApi могли измениться; код работает через отражение).
3. В игре нажать Pair у Smart Switch и Smart Alarm. На обеих вкладках должна появиться одна карточка на правильном сервере. Нажать «Проверить и добавить»: устройство появляется в обоих списках только после успешного `getEntityInfo`; при ошибке карточка остаётся с причиной. Повторный запуск приложения не должен терять карточку; повтор того же FCM не должен создавать дубль.
4. Подключиться к серверу, выбрать другой сервер во второй вкладке — выбор должен совпасть в первой.
5. Включить 🔔 у Smart Alarm, канал «Overlay», вызвать срабатывание в игре. Затем «Team Chat и Overlay» — проверить сообщение в чате команды и запись в «Журнале доставки». Отключить соединение Rust+ → Team Chat должен честно показать «не отправлено».
6. Смарт-переключатель: Включить/Выключить (успех только после подтверждённого чтения).
7. Доступность: временно отключить питание/разрушить тестовый Smart Switch (или удалить его в игре) → через ~90 с «НЕДОСТУПНО» и одно уведомление; вернуть → уведомление о восстановлении. Отключить сам сервер/сеть → уведомлений о недоступности устройств быть не должно.
8. Игроки: добавить игрока в наблюдение → индикатор серый, «не подтверждено». «Связать SteamID64» → зелёный при присутствии. Выйти игроку с сервера → после N проверок одно уведомление «… покинул …» выбранным каналом; возвращение — без уведомления.
9. Проверить `Поиск сервера` → открыть сервер → он попадает в базу; через несколько циклов «Где ещё наблюдался» показывает серверы.
